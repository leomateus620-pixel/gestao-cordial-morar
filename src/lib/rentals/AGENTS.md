- Owner payouts (repasse): pure rules in src/lib/rentals/payout-model.ts (integer cents, line origin/sign/recipient/rule; never negative, never above received, destination version change voids approval, only `confirmado` shows as "Repassado"); rental_payouts* tables are service-role-write only — why: finance must audit every line and no double or premature payout.
- Rental contract drafts: approved texts live in src/lib/rentals/contract-templates/<brand>-<guarantee>.txt with {{placeholders}}; insurer clauses live in rental_insurers (admin-edited); filling is pure in contract-generator.ts and download is blocked while any [PREENCHER] marker remains — why: the legal text stays reviewable and no contract leaves with blanks or "xxx".
- Guarantor spouse lives on rental_contract_guarantors.conjuge (validated by guarantor-spouse.ts, never a separate guarantor); generated contracts are saved via a content-hash path (idempotent) and success shows only after the document is registered; entry needs a reviewed contract doc, exit needs entry `concluida` + inspection_documents row (one per kind per contract) — why: no duplicate files, false success or premature exit inspection.
- Rentals competence is a single URL param (`competencia`, AAAA-MM; current São Paulo month is omitted) navigated only via `rentalSearch` in competence-nav.ts; RentalExpandedDetails is controlled and card badges come from one batched `listRentalCompetenceStatus` (user RLS; boleto hidden while production issuance is locked, NF in test mode informational) — why: batch receipts without re-picking the month and never show a wrong pending.
- `rental_confirm_workflow_file` treats a missing/JSON-null guarantee `person` as no guarantor (only `fiador` requires one) and the client omits the key; UI errors in the contract flow go through workflow-errors.ts — why: non-guarantor drafts crashed with raw Postgres errors.
